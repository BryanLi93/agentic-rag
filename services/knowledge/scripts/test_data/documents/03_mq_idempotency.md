# MQ 与幂等处理笔记

这份文档围绕消息队列的异步、削峰、解耦，以及 Consumer 为什么必须考虑幂等展开。它适合测试 AI 长任务、消息重复投递、task_id、request_id、库存扣减和后台任务这些问题。

## MQ 的三个核心价值

MQ 是 Message Queue，消息队列，是一类用于系统之间暂存和传递任务或事件的消息中间件。Kafka、RabbitMQ 等是具体实现。

最先需要记住三个价值：异步、削峰、解耦。

异步表示 API 接到请求后，不一定同步完成所有耗时工作，而是先把任务写入 MQ 并快速返回，后台 Consumer 再继续处理。削峰表示高并发到来时，任务可以先堆积在队列里，Consumer 按自己和下游系统能够承受的速度持续消费，避免瞬时流量把数据库、模型服务或第三方接口压垮。解耦表示生产者只需要发布事件，不必直接依赖所有后续处理服务。

## AI 长任务为什么适合 MQ

例如用户上传一个大文件，需要经历：

`文件解析 → AI 处理 → 生成结果 → 持久化`

如果整个流程需要几十秒甚至几分钟，不适合让 HTTP 请求一直占着连接等待。更合理的结构是：

`API → MQ → Worker / Consumer → 后台任务`

API 可以先返回 `task_id`，前端之后通过轮询、SSE 或 WebSocket 获取任务状态。即使用户关闭页面，HTTP 请求生命周期结束，后台任务仍然可以继续执行。

## 幂等是什么

幂等不是某个框架功能，而是一种业务操作性质：同一件业务操作重复执行多次，最终业务结果和只执行一次相同。可以把它理解为系统对重复请求或重复消息有免疫力。

“把头像设置成 A”“把订单状态设置为已支付”通常比较容易天然幂等，因为重复执行后最终状态不变。相反，“库存减 1”“余额增加 100”天然不是幂等操作，因为重复一次就会多产生一次副作用。

## 非幂等操作怎么保护

关键不是让 `-1` 这个数学操作本身变成幂等，而是让系统识别“这是不是同一笔业务操作”。

例如订单 A 需要扣 1 件库存：

1. 用 `order_id`，或者独立的 `request_id / message_id` 作为唯一业务标识。
2. 第一次消费时完成扣库存，并记录“订单 A 的扣库存操作已处理”。
3. 同一条消息因为超时、重试或重新投递再次到达时，先检查这个业务标识。
4. 如果已经处理过，直接返回或跳过，不再重复扣库存。

这样同一个业务操作来 1 次和来 5 次，最终库存都只减 1。

## 为什么 MQ 经常和幂等一起问

消息系统为了避免消息丢失，通常会设计 ACK、重试或重新投递机制。只要存在重试，Consumer 就必须接受“同一条业务消息可能到达不止一次”这个现实。因此面试里常见的追问链路是：

`可靠投递 / 重试 → 可能产生重复消息 → Consumer 必须幂等`

幂等 ID 只是起点，真正落地时还要考虑状态记录和并发竞争。例如两个重复消息几乎同时到达，如果只是“先查有没有，再插入”，本身仍可能发生竞态，通常还需要数据库唯一约束、条件更新或事务把检查与写入保护起来。

## MQ 和 async/await 不是一回事

`async/await` 主要解决单个进程内部如何以非阻塞方式组织异步代码；MQ 则负责跨请求、跨进程、跨服务地保存和传递任务。HTTP 请求结束后，本地的普通异步函数未必具备可靠持久化和失败恢复能力，而 MQ 可以让任务生命周期独立于单次请求。

最短记忆可以是：高峰来了，API 快速返回，后台 Consumer 按消息队列持续处理；为了抵抗消息重试和重复投递，所有有副作用的 Consumer 都要设计幂等保护。
