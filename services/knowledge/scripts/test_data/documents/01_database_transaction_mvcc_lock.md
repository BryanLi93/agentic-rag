# 数据库事务、MVCC 与并发锁笔记

这份文档围绕数据库事务和并发更新展开，适合测试“事务、隔离级别、MVCC、乐观锁、悲观锁、并发扣库存”这些问题。核心不是死背数据库内部实现，而是建立一条完整的业务心智链路：并发请求进入系统后，哪些操作需要事务，读写如何减少互相阻塞，写写冲突又如何保证最终结果正确。

## 事务解决什么问题

事务把一组相关数据库操作当成一个整体执行：要么全部成功并提交，要么中途失败后全部回滚。典型下单流程可能包括创建订单、扣库存、写支付记录。如果前两步成功、第三步失败，而系统没有事务保护，就会留下“订单存在、库存已扣、支付记录却不存在”的半完成状态。

在 Spring Boot 项目里，事务通常放在 Service 层，因为 Service 才知道哪些 Repository / DAO 操作共同组成一次完整业务动作。Controller 只处理 HTTP 边界，DAO 只负责具体数据访问，都不适合作为业务事务的主要边界。

## 隔离级别的作用

多个事务并发执行时，需要规定“一个事务能够看到另一个事务哪些状态的数据”。这就是事务隔离。常见隔离级别从弱到强包括 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ 和 SERIALIZABLE。

当前最重要的理解不是逐条背异常，而是：隔离级别解决的是并发事务之间的数据可见性问题。隔离越强，事务之间互相干扰越少，但通常并发成本也更高。

## MVCC 的直觉

MVCC 是 Multi-Version Concurrency Control，多版本并发控制。它的核心思路是为同一条数据保留不同版本，让正在执行的事务可以按可见性规则读取一个稳定版本，而不是所有读操作都必须等写事务结束。

例如库存原来是 10，事务 A 正在把它改成 9，但还没有提交。事务 B 此时查询，仍然可以看到之前稳定的 10。A 提交后，新事务再读取时才看到 9。这里旧版本不是错误数据，而是给特定事务提供的稳定快照。

因此可以先用一个简化模型理解：MVCC 的价值是让读写尽量少互相阻塞，提高并发能力。但真实数据库里 MVCC 和锁通常是配合使用的，并不是两个互相替代的机制。

## 写写冲突与锁

如果两个事务都要修改同一条数据，就可能出现写写冲突。例如库存为 10，A 和 B 同时读取到 10，然后都执行“减 1”。如果没有并发保护，两次更新可能都基于旧值写回 9，最终只减了一次。

悲观锁的思路是先假设冲突很可能发生，所以先锁住数据再修改。直觉上就是“我先占住这条数据，别人要改就等我”。它适合冲突概率较高、业务必须强控制的场景，但会增加等待和阻塞。

乐观锁不提前阻塞，而是在真正更新时检查数据有没有被别人改过。常见做法是增加 version 字段：读取时拿到 version = 3，更新时带上 `WHERE id = ? AND version = 3`。如果受影响行数为 0，说明版本已经变化，本次更新发生了并发冲突，应用层再决定失败、提示或重试。

## 乐观锁和 MVCC 不要混淆

乐观锁通常是“应用层 + 数据库条件更新”共同实现的并发控制策略；MVCC 则是数据库为了事务可见性和并发读写而使用的内部机制之一。两者都和并发有关，但解决问题的层级不同。

面试或排查时可以记住这条链路：

`并发请求 → 事务 → 隔离级别 → MVCC / 锁 → 乐观锁 / 悲观锁 → 并发更新正确性`

如果只问最短版本，可以回答：事务保证一组数据库操作要么全成功要么全失败；隔离级别规定并发事务的数据可见性；MVCC 通过多版本减少读写阻塞；多个事务竞争修改同一份数据时，还需要锁或乐观并发控制保证更新正确。
